## Authentication and routing

The stateful splash owns one initialization future with an error state and Retry. Firebase services are constructed only after initialization succeeds. AuthService owns account creation, login, logout, and the private profile workflow. `authStateChanges()` selects signed-out screens or the profile gate. A missing profile presents a recovery form under the same UID; it never creates a second account. A transaction creates a profile only when absent, preserving its original timestamp. Authentication and profile creation are separate operations, not an atomic cross-service transaction.

## Data model and field ownership

| Path/field | Writer | Permitted modifications |
|---|---|---|
| users/{uid}.uid | Authenticated owner | Must equal path; immutable |
| firstName, lastName | Owner at creation | Nonempty, max 60 characters; immutable |
| role | Owner at creation | Only `member`; no administrative privilege |
| registrationDateTime | Server transform | Creation request time; immutable |
| messages/{id}.text | Authenticated author | Author can edit; 1–2000 non-whitespace characters |
| authorUid | Authenticated author | Must equal Firebase UID; immutable |
| authorName | Authenticated author | Must match private profile at creation; immutable |
| createdAt | Server transform | Creation request time; immutable |
| editedAt | Author's server transform | Null at creation; request time on edit |
| users/{uid}/postReceipts/{id} | Owner, atomically with message | Exactly messageId and server createdAt; immutable, never deleted |

Profiles are readable only by their owner, and collection listing is denied. Signed-in users can read board content. Other users cannot edit/delete a message even through direct SDK or REST calls. All unspecified paths and operations are denied. Rules require both halves of message/receipt creation and prohibit receipt reuse.

## CRUD, live updates, and duplicate prevention

BoardService centralizes all message operations and maps snapshots to typed BoardMessage objects. The newest 100 messages stream in descending server timestamp order. StreamBuilder owns its subscription; the stream is created once in the board state. Empty, loading, error, author controls, edit dialogs, delete confirmations, and timestamps are rendered explicitly.

One pending logical submission per user is saved locally as a stable ID and text before the network transaction. Retry and app restart reuse it. A transaction reads an immutable receipt; if absent, it writes the message and receipt together. An existing receipt means the operation already completed, including when the message was subsequently deleted. The submit button and service guard also prevent rapid repeated calls in one process.

A concurrent commit can encounter permission-denied before SDK conflict retry because the receipt is immutable. The service checks that receipt using a **server** read before recognizing the attempt as complete. Otherwise it preserves the pending submission and reports the error. It never blindly treats a denied write as success.

Cost: one receipt read and two document writes for a new logical submission, plus rules-dependent profile/receipt reads; a replay usually costs one receipt read. Receipts accumulate indefinitely to prevent resurrection after deletion. Transactions require connectivity. Posting offline retains the local pending payload and requires explicit Retry after reconnect. Ordinary Firestore edit/delete writes may queue offline; they are not equivalent to transactions. Pending text is unencrypted app-private preferences, names/passwords/tokens are not separately stored by application code. Firebase SDKs manage their own auth and Firestore persistence. Clearing app data can lose an unsent draft.

A dedicated release key is stored outside this repository at `~/.vaultboard-signing/release.jks`; its password is kept privately alongside it. `android/key.properties` is ignored.
