# Het Jani — reflections

Edited from the student's personal input received November 22, 2026, combined with documented implementation results. The student followed and reviewed the work; these reflections do not claim independent authorship of all code or tests.

1. **Expectation versus obtained result:** Before this project, I understood basic Flutter widgets and Firebase login/database ideas, but I was less clear about authorization and retries. My expectations supplied for this later review were that cloud posts would survive closing the app, rebooting, and clearing local data. The earlier tests support that distinction. CRUD and live synchronization worked, while the first concurrent submission test revealed a denial edge case. My lesson is that a saved cloud record, a local session, and an unfinished submission have different lifecycles. These expectations were supplied after the original tests, not recorded before them.

2. **Debugging evidence:** I mainly followed and reviewed ownership rules, real-time updates, and duplicate prevention. The concurrent transaction test initially produced permission-denied because immutable receipt rules could reject the losing commit before the SDK retried it. The fix checked the receipt from the server before recognizing completion; reruns verified one post and no resurrection after deletion. Loosening receipt rules was rejected because it would weaken the permanent completion record. I was surprised that hiding Edit/Delete controls does not secure the database.

3. **Improvement plan:** I would prioritize pagination and stronger auditability as the message count grows. The current rules already enforce immutable authorUid and createdAt, so that part of my initial improvement suggestion is already implemented. My next concrete change would be cursor-based access to older messages, supported by schema/rules regression tests and version checks for conflicting edits.

4. **Privacy and placement judgment:** On a shared phone, I would prefer the app to forget my login and unfinished message so another person could not see my account or draft. The current app instead persists the Firebase session and UID-scoped pending text for convenience and retry safety. It does not separately store passwords or tokens in preferences, but SDK-managed credentials and caches still exist. A future shared-device mode should explicitly sign out and handle unfinished drafts; my preference is not implemented merely because I stated it here.

5. **Cloud versus device:** Committed messages, profiles and immutable receipts belong in Firestore. Preferences and unfinished drafts may belong on the device, with clear privacy and data-loss trade-offs. Clearing app storage removes local session/cache/pending data, not cloud posts. Keeping a pending ID helps prevent duplicates, but an unsent draft can be lost if the app's data is cleared.

6. **Scaling and maintainability:** At 10,000 users and 100,000 messages, live listeners can multiply reads and receipt storage keeps growing. The newest-100 query bounds the live view but does not provide older-message pagination. I would add cursor pagination, monitor usage, and keep rules tests alongside schema changes. Receipt retention needs careful design because deleting completion receipts could allow a late retry to recreate a deleted message.
