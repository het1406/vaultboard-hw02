# Reflection evidence and remaining student input

These are technical findings for Het Jani to review, not invented first-person experiences.

1. **Expectation versus result:** The first automated full CRUD and live-client tests passed. The first concurrent-submission test failed with permission-denied, despite there being one committed logical post. The student's original expectation is unavailable and must be supplied before a personal reflection can be finalized.
2. **Debugging:** The emulator trace identified competing transaction authorization failure. Both transactions saw no receipt initially; immutable receipt rules rejected the losing commit. The fix checks the receipt from the server after permission-denied and recognizes completion only if it exists. The rerun passed concurrent submissions and post-deletion replay. Loosening receipt-update rules was rejected because permanent immutable receipts enforce the stronger late-retry guarantee.
3. **Improvement:** Add cursor pagination and version checks for concurrent edits. The current 100-message limit bounds listener size but hides older messages. Version checks could warn rather than silently accept a later edit over another edit. Student priority and rationale remain to be supplied.
4. **Privacy:** The app does not separately save passwords, tokens, or private profiles in preferences. A UID-scoped pending ID/text is stored to survive retries. Firebase SDK auth persistence and cached board records remain on device. Pending text is not encrypted; convenience has a privacy cost on a shared device.
5. **Cloud/device placement:** Firestore owns committed messages, private profiles, and receipts. Device storage holds pending drafts and SDK-managed session/cache state. Device data can be erased independently of cloud data. A receipt cannot recover text never sent to the cloud.
6. **Scaling:** At 10,000 users and 100,000 messages, many active listeners amplify read costs and receipts grow with every post. Pagination, bounded queries, retention policy design, usage monitoring, and versioned schema/rules tests are practical next steps. Do not delete receipts casually: that would permit late retries to resurrect deleted messages.
